### Findings that changed the runbook (all derived from the reviewed source at f9285d6)
1. **The TCC grants do NOT have to happen inside D4's five-minute pairing window.**
   `CaptureController.start` (`CaptureController.swift:230-246`) requires only
   `loadControlSecret() != nil` - which the app writes for itself at launch - and calls
   `source.start` at `:242`, *before* the first publish at `:250`. Pairing is needed only by that
   publish. So an **unpaired** `start` still raises both prompts; the publish then fails
   `missingCaptureBearer`, which `CaptureFrameRetryPolicy` classes as not retryable, so the
   controller unwinds the source and throws - but the user's two decisions are already durable,
   because TCC records the click, not the capture outcome. Both iteration 22's "Next" note and the
   old E3 candidate asserted the opposite coupling. Splitting them removes the worst failure mode of
   the human step: a mis-timed prompt answer can no longer burn a minted payload.
   **Derived, not observed** - E3 itself is the confirmation; if the unpaired `start` behaves
   differently, fall back to the coupled sequence (mint, pair, then start once).
2. **Prompt order is fixed by the source, not by chance.** `NativeDualCaptureSource.start` admits
   system audio first (`:191`), microphone second (`:192`). System audio has no request API -
   `AudioHardwareCreateProcessTap` inside `SystemAudioTap.start` *is* the request, called inline on
   the control thread - while the microphone is the asynchronous
   `AVCaptureDevice.requestAccess(for: .audio)` that leaves the lane `pending`. So System Audio
   Recording is always the first alert, and it is the only one that can block.
3. **The CLI cannot launch the app on this host, and nothing says so anywhere.**
   `NSWorkspaceLaunchServicesCaptureAppLauncher.launch()` (`CaptureCommandLine.swift:69`) reads
   `MOSS_CAPTURE_APP_URL` and throws `launchServicesUnavailable` when it is unset. Nothing in the
   product, in `install-app.sh` or in a shell profile sets it - the only occurrences in the tree are
   two test fixtures and one `env.pop` in `tests/live_integration_replay.py`. That is exactly why
   the installed CLI answered `{"ok":false}` `rc=70` in iteration 22: not "no helper running" as
   recorded, but "no helper running **and** no way to start one". Had the operator been handed
   `mtd-capture pair` as the first command, it would have failed with an opaque `{"ok":false}` and
   burned the 300 s payload. The runbook therefore starts with an explicit GUI launch.
4. **A hung `start` is the expected appearance of an unanswered prompt.**
   `UnixDomainControlServer.serve()` is a serial accept loop (`CaptureSecurity.swift:897-902`) and
   `UnixDomainControlClient` sets no `SO_RCVTIMEO` (no timeout symbol exists in that file). So while
   the tap call waits on the alert, `start` blocks with no timeout and every other `mtd-capture`
   command - `status` included - queues behind it. This is M36's consequence made concrete: a hung
   `status` is not evidence the app died. Diagnose with `pgrep`/`sample`, never by killing the app.
5. **The pairing payload is a stdin argument.** `CaptureCommandLine.swift:114-130`: `pair` takes
   `--server` from argv and the payload from `input.readAll()`, with empty stdin -> `rc=65`. Pasting
   it into an interactive `mtd-capture pair` and pressing Ctrl-D satisfies the PRD's secret-hygiene
   clause for free - no argv, no file, no history entry.

### The first attempt was killed at 10 minutes - what that cost and what it taught
The first `merge-keeper.sh` invocation ran in a time-capped foreground shell and was killed at 10
min. Facts, not inference: the last artifact written in its worktree was at 04:20:29, 17 s after the
worktree was born (04:20:12), and nothing was written for the remaining ~10 min. Re-running each
stage by hand in that same worktree afterwards passed - `swift test` 1.15 s, tracer 16.5 s, full
pytest 67.4 s - and a fresh full run of the script then finished in ~95 s. So the stall is
**unexplained**; the honest suspicion is a first-run macOS security assessment of freshly built
binaries at a new path, and it was not proven because the stuck process was killed by the cap before
anyone sampled it.
The concrete damage was recoverable but not obvious: SIGTERM skips the script's EXIT trap, so the
kill left a linked worktree with `main` checked out and the merge staged. A branch can be checked
out in only one worktree, so the retry would have failed at `git worktree add … main`. Recovery:
`git -C <wt> merge --abort && git worktree remove --force <wt>` - both run, both confirmed, `main`
still at `f9285d6` at that point (the killed run never committed).

### Learned
1. **Run the irreversible step where a timeout cannot kill it.** The merge is not slow, but it is
   the one command in this loop whose interruption leaves shared state (a worktree owning `main`)
   behind. Background it and poll; the cap is an orchestration artifact, not a property of the work.
2. **A fence you advance is stronger than a fence you override.** Moving `expected_main` inside the
   script cost one line and bought a rehearsable refusal of a third merge; `RALPH_MERGE_MAIN_BEFORE`
   on the command line would have left nothing behind to test.
3. **Prove the no-op before performing it.** `git merge-tree --write-tree` answered "this join
   produces exactly your current tree" before any history was written, which turned the history join
   from an argument into a measurement.
4. **A killed run is still evidence.** The stranded worktree carried the staged merge, so the merged
   tree could be measured stage by stage - which is how `swift test` and the tracer were cleared as
   the stall's cause before spending another full run.
