CRITERION BY CRITERION
--------------------------------------------------------------------------------

1. "P0: stop discarding captured audio."

   The PRD quotes `capture_pipeline_page.html:962` -> `if (st.sendPaused || st.sendInFlight)
   return;`. That line is NOT on this branch's base. `git log --all -S sendInFlight --
   prototypes/browser-capture-feasibility/capture_pipeline_page.html` puts it only on
   `afk2/f1-canary-fixes` (a5f3cc9, 131c2a1, f8f9d6e), which `git merge-base --is-ancestor
   afk2/f1-canary-fixes dev` reports is NOT an ancestor of `dev`. `dev`'s page (896 lines)
   fires an unguarded `fetch` per worklet message with `const sequence = st.seq++` at emit
   time: unbounded concurrent POSTs, not a drop. Iteration 2 of the loop reported exactly
   this, and it was right.

   The branch nonetheless implements the right transport: a per-lane FIFO bounded by
   `max_retained_samples / frame_samples`, one serial sender per lane, the wire sequence
   assigned only as the head is dispatched and advanced only after a 200, and — when the
   FIFO does overflow — a cumulative `droppedFrames`, a `discontinuityPending` flag that
   marks the next admitted frame, and a heartbeat that now reports both.

   PROVEN, not just read: `probe_frame_loss_falsification.py` runs the committed page's real
   transport script and re-inserts the historical guard as a source mutation.
     - current page : 49 admitted / 50 elapsed-cadence frames, 0 dropped, per-lane
                      concurrency 1.
     - `inflight_drop` mutant : 25 admitted / 49 emitted (49 % loss), `dropped_frames: 0`,
                      `discontinuities: 0`, heartbeat still reporting zero — the historical
                      silent-loss signature, reproduced.
     - forced overflow (capacity 4): 31 dropped, 22 discontinuities, heartbeat route carries
                      `dropped_frames: 31`, and 44 admitted frames carry `discontinuity: true`.

2. "The assertion that would have caught it."

   `admitted_frames_approximately_match_elapsed_cadence` (probe_slow_post_characterization.py
   :257) is NOT a tautology. Scored with the committed probe's own `_lane_summary`, it is TRUE
   on the current page (delta 0) and FALSE on the `inflight_drop` mutant (delta -24).

   Its G7 twin, `admitted_frames_approximately_match_hidden_elapsed_cadence`
   (probe_g7_hidden_tab.py:253), was falsified separately using probe_g7_hidden_tab's OWN
   `_admission_cadence` over a rebuilt route-acceptance/telemetry join: delta 0 on the current
   page, -24 on the same mutant. Both halves of the new gate can fail.

   The other two assertions in the same dict do NOT catch the defect: on the same mutant,
   `per_lane_frame_posts_are_serial` and `wire_sequences_follow_admitted_worklet_order` both
   stayed TRUE. `wire_sequences == range(n)` is contiguous by construction and should not be
   read as loss detection.

   Still tautological in probe_g7_hidden_tab.py, and left in place by this branch:
     - `each_lane_has_contiguous_hidden_accepted_sequence_progression` (:250) — the records it
       scores are ROUTE ACCEPTANCES, and `moss_transcribe_diarize/app/live_ingest.py:137`
       admits a frame only when `frame.sequence == lane.next_sequence`. Accepted sequences
       are therefore 0,1,2,... by construction; no input can make this false.
     - `strict_v2_accounting_matches_descriptor_frames` (:263) — `accepted_samples` is
       accumulated as `start + sample_count` (live_ingest.py:148), so with a fixed
       `sample_count` (already asserted separately) this is arithmetic identity.
   Both are harmless now that the cadence assertion exists, but neither is evidence.

   (c) I could NOT re-run it. See the environment blocker below. What I could re-run without a

4. "recreateSession."

   `recreateSession` does not exist on `dev` at all — this branch adds it, together with the
   `#recreateSession` button, `requireSessionRecreation` (called from the real 409 branch of
   `sendQueuedFrames`), and `drainFrameSends`. It is NOT dead code at the route: the only path
   that enables the button is a real HTTP 409 on the real frame send.

   Verified against the race the PRD names, on the real page source: while the peer lane's
   already-admitted POST is still resolving, the page keeps `live_session_id: old-session` and
   `microphone.send_in_flight: true`; the old session's `next_sequence` reaches 1 BEFORE the
   lane's `seq` is reset to 0; a forced 503 on the first recreate leaves
   `recreate_disabled: false`; the retry lands on `new-session` and both lanes resume at wire
   sequence 0 with no 409 on the fresh session. Removing the drain (`no_drain` mutation) breaks
   it: the microphone lane never resumes and `new-session.microphone.next_sequence` stays 0.

WHAT THE TESTS DO NOT COVER
--------------------------------------------------------------------------------

* No AudioWorklet, no Chrome scheduler, no real HTTP stack and no hidden-tab intensive
  throttling in `page_sender_harness.mjs`. It measures transport SEMANTICS only. Anything that
  depends on Chrome's timer/throttling behaviour is covered only by the committed browser
  artifacts, which I verified by content but could not re-run.
* No real microphone, no display capture, no attended Gate-1 checklist, no real provider, no
  model inference anywhere in x1's evidence.
* No test asserts the heartbeat's `dropped_frames` against a REAL browser overflow; the
  truthfulness proof is from the Node harness only.
* Overflow is only ever forced by shrinking `max_retained_samples`. Nothing measures whether
  the production 40-frame queue (320000/8000) is deep enough for a real slow uplink, so the
  drop rate under real network conditions is unmeasured.
* The 409 -> recreate path is proven only through the stub-lane probe seam (D3). A real
  worklet-driven session that 409s mid-capture is untested.
* No backoff on a repeated non-409 error response: `sendQueuedFrames` retries the same FIFO
  head on the next worklet message, so a permanently-rejected head (e.g. HTTP 400) will fill
  the queue and convert into counted drops. That is truthful but untested and unbounded in time.
* `recreateSession` early-returns when `!bothLanesHaveSignal()` without any user-visible
  message. Unreachable in practice (a session only exists after both lanes had signal) and
  untested.
* Nothing verifies the added `X-Prototype-Lane` request header is harmless to the real
  deployed service; it exists only so the probes' middleware can attribute a lane.
