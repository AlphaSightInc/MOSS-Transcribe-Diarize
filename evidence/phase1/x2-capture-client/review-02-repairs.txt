# x2-capture-client — adversarial review, artifact 2: what was still broken, and the repairs
# Re-run everything below from the repository root.

Two defects survived the loop's self-reported COMPLETE. One it escalated and left
unbuilt; one it introduced.

================================================================================
REPAIR 1 — the heartbeat scheduler silently drops a heartbeat (introduced by the branch)
================================================================================

## The defect

`scheduleHeartbeat` cleared its in-flight marker from a `.finally()` attached to the
promise it returned:

    this.heartbeatFlush = this.flushHeartbeat().finally(() => { this.heartbeatFlush = null; });

`flushHeartbeat`'s drain loop can therefore have already stopped while `heartbeatFlush`
is still non-null, because the `.finally()` callback runs a microtask later. A
`scheduleHeartbeat` landing in that window sets `heartbeatPending` and starts nothing.
Nobody ever sends it.

The pre-branch client did not have this hole -- it re-checked inside `finally`:

    } finally {
      this.heartbeatInFlight = false;
      if (this.heartbeatPending && this.session) void this.flushHeartbeat();
    }

so this is a regression the branch introduced while rewriting the scheduler.

## Reproduction (before the fix)

Scanning microtask offsets between two schedules, with a client whose session is set and
whose fetch resolves immediately:

    offset 0  heartbeatFlush=true   sent: ["degraded", "capturing"]
    offset 1  heartbeatFlush=true   sent: ["degraded"]              <-- LOST
    offset 2  heartbeatFlush=false  sent: ["degraded", "capturing"]
    offset 3+ heartbeatFlush=false  sent: ["degraded", "capturing"]

## Why it matters

The worst case is `stop()`, which does `await this.scheduleHeartbeat("stopped")`. Landing
in that window returns the already-settled previous flush promise, so `stop()` proceeds
to the authenticated stop route having never sent the `stopped` heartbeat -- which is
precisely the one server-side behaviour PRD defect 2 exists to enable ("Audio capture
stopped."). The periodic path self-heals within one frame period; the final one does not.

It also silently drops lane-failure and lane-recovery news, which is how a sealed lane or
a cleared warning fails to reach the operator.

## The fix

`frontend/src/capture/captureClient.ts` -- a `heartbeatFlushing` boolean set
synchronously at schedule time and cleared in `flushHeartbeat`'s own `finally`, i.e. in
the same synchronous step the drain loop exits in. No window exists between the loop
stopping and the marker clearing.

## Failing-before / passing-after

Two committed regression tests in `frontend/src/capture/captureClient.test.ts`:

  - "sends a heartbeat scheduled at any microtask offset after the previous one"
  - "still posts the final stopped heartbeat when stop() lands in that window"

Reverting only the scheduler to its pre-fix shape and re-running the gate:

## The state as received

The branch shipped `browser_track_ended` and `browser_audio_context_suspended`, surfaced
`browser_microphone_permission_denied`, `browser_capture_request_rejected` and
`browser_surface_audio_missing` through a pre-session callback, and stopped there.
`browser_sustained_clipping` and `browser_microphone_silent` were escalated at iteration
8 as blocked on "a real-browser sustained-clipping/microphone-silence threshold
measurement" owned by `prototypes/browser-capture-feasibility/`, which x2 does not own.

That blocker does not hold up. The charter rules both behaviours binding
(`docs/phase1-afk-charter.md` section 4: "Clipping. Meter and warn on sustained
full-scale"; "Silent mic lane -> the status line must name how to change Chrome's default
input"), the server already carries the copy for both, and the measurement needs no
browser at all: it needs real 16 kHz audio framed at the descriptor geometry, which is
already in the tree and readable. Nothing about it required editing another ticket's
files.

Thresholds chosen from that, and now compiled into the client:

    CLIPPED_SAMPLE_MAGNITUDE   32766.5/32767  (i.e. the encoder emits exactly +/-32767)
    CLIPPED_FRAME_FRACTION     0.01           (1% of a frame at full scale)
    SUSTAINED_CLIPPING_FRAMES  4              (2.0 s)
    SILENT_MICROPHONE_FRAMES   20             (10.0 s, microphone lane only)

The probe is the standing gate on those four numbers, not decoration. Mutation sweep:

    SUSTAINED_CLIPPING_FRAMES = 1  -> PROBE FAIL: a 0.5 s overload on real speech would be

                                     4 consecutive frames but would not warn;

    CLIPPED_FRAME_FRACTION = 0.5   -> PROBE FAIL: local.wav at gain 32 ... would not warn

    SILENT_MICROPHONE_FRAMES = 200 -> PROBE FAIL: leading-060s.wav carries 120 consecutive
                                     genuinely silent frames ... a dead lane would never be
                                     reported

## The safety property that decided the design

Both conditions ride `state: "degraded"`, never `"failed"`.
`LiveHelperFailureCoordinator.observe` calls `LiveV2Session.fail_lane` for every lane a
heartbeat reports as `failed`, permanently sealing it, and `_terminal_reason` tears the
whole session down when both lanes are failed. Reporting "your microphone is too loud" as
`failed` would end the meeting. `prototypes/browser-capture-feasibility/NOTES.md`
measured the same thing directly: "a `degraded` fact remained in helper presence without
failing a lane".

Both conditions are also recoverable -- they clear themselves when the audio recovers,
unlike the `failed` latch.

## Failing-before / passing-after

Three committed tests in `frontend/src/capture/captureClient.test.ts`, all driven through
the real worklet port rather than by calling the detector:

  - "reports sustained full-scale audio as a degraded lane, and clears it on recovery"
    (3 clipped frames stay quiet; the 4th degrades the lane; a clean frame clears it)
  - "names the silent-microphone remedy only for the microphone lane"
    (40 silent system frames stay quiet; 19 silent mic frames stay quiet; the 20th
    degrades the mic lane; a clean frame clears it)
  - "never reports a metered condition as `failed`, which would seal the lane
    server-side" (both lanes in their worst metered state at once, never `failed`; a real
    ended track still latches `failed` and outranks the metered reason)

All three fail on the branch as received, because the two codes did not exist.
