WHAT THESE TESTS DO NOT COVER
  * Timing-attack resistance is NOT demonstrated. `EqualityTrap` proves the code calls
    `hmac.compare_digest`; it measures nothing. No wall-clock timing is taken anywhere,
    and none should be inferred. Three reasons the property is weaker than it reads:
      - the values compared are SHA-256 digests, not the bearers. Learning digest-prefix
        timing does not let an attacker construct a bearer, because they cannot invert
        the hash. This is defense in depth, not a closed channel.
      - `_capture_for_digest` returns on first match and iterates `self._devices` in
        insertion order, so the *number of comparisons* varies by which device matched.
        The lookup as a whole is not constant time even though each comparison is.
      - `_view_for_digest` has the same shape over `self._sessions`.
  * No test asserts anything about the deployed service. Nothing here was run against
    ga0-alienware-rtx4070ti; every probe binds its own loopback port.
  * The revocation marker's digest is now on disk while revoked. It cannot grant --
    `_capture_for_digest` refuses a revoked device before reading it, and the live shared
    principal is rebuilt from configuration every start -- but an attacker who can READ
    live-auth.json could brute-force a weak operator-chosen shared token offline. Not
    tested, and judged acceptable only because that attacker can already read the 0600
    token file holding the plaintext under the same uid. If the shared token ever stops
    being a high-entropy value, re-open this.
  * An attacker who can WRITE live-auth.json still owns the deployment (they can add any
    device). No integrity protection on the state file is tested or claimed.
  * Concurrency is untested: `_persist()` is not locked, and two processes sharing one
    state dir would race. The charter forbids uvicorn workers, so this is out of scope
    but is not "safe" -- it is "not exercised".
  * Pairing with an EXISTING non-reserved device_id still silently replaces that device's
    token (`exchange_pairing` overwrites any non-revoked record). The pairing code is
    loopback-minted, so this is inside the accepted one-trust-domain model recorded in
    .wayfinder, and I did not change it -- re-pairing after a device reinstall depends on
    it. Flagged for the orchestrator, not fixed unilaterally.
  * No test covers the token file being replaced while the process runs; the token is
    read once at startup by design.
  * The marker is a kill switch WITHIN a configuration, not above it. Rotate away from the
    revoked token and then deliberately configure it again after any `_persist()` has run,
    and it works: the marker is gone by then. Configuration is the source of truth by
    design (T-01 keeps the shared token a configuration mode, not an authority store), but
    it is an explicit boundary, not an accident, and nothing tests it.
  * Peer admission is exercised only positively in the new probe -- every request in
    `probe_shared_revocation_process_restart.py` comes from 127.0.0.1. The non-loopback TLS
    path and the reserved-id rejection are covered by `probe_uvicorn_wire_auth.py`, which
    sources from a real private address, and loopback-only revocation is covered by unit
    tests (tests/test_live_auth.py:350, :446). No single artifact covers all three.
