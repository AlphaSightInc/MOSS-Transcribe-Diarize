# Gemini runtime seam probe (pane P63)

## Contract before implementation

- **Structural question:** Can one session-local stream of mixed 16 kHz PCM and engine updates be published through the existing `LiveSession` snapshot authority without changing the HTTP/UI contract?
- **Minimum primitives:** retained audio position (absolute samples), engine update (preview, committed/revised, terminal), stable meeting speaker ID, session publication state. The position binds words to the tape; the update carries the only new provider output; the speaker ID is the UI-visible identity key; publication state owns lifecycle and revisions. Remove any one and either time, identity, or lifecycle becomes ambiguous.
- **Invariants:** input frames are retained before provider work; committed rows have absolute ordered sample bounds and canonical speaker IDs; a revision changes an existing visible row rather than duplicating it; Stop settles to `final` or a visible failure; sessions cannot share engine state; the existing snapshot/event schema stays intact.
- **Assumptions / unknowns:** `LiveSession` may require sequential frozen prefixes and reject rolling rewrites. Exact engine word source, window policy, speaker continuity, live latency, quality, and spend are unmeasured pending the bake-off. Voiceprint extraction from committed Gemini intervals may need a separate measured design.
- **Falsifier:** a scripted preview, commit, relabel, and terminal revision cannot be represented by existing `LiveSession` calls and consumed by the unchanged poller shape; or Stop cannot expose a failed finalization without hanging.
- **Tool decision:** inspect `LiveSession` and the current runtime/publication path to find the smallest seam. Run a one-command throwaway state probe against `LiveSession`; its acceptance/refusal counts decide whether to reuse it. Then use offline TDD through the runtime's public methods. Run focused existing tests only if they can detect an actual HTTP/runtime contract break.

## Hypothesis

`LiveSession` remains the snapshot authority. A thin per-session adapter converts engine updates to its publication calls; all capture, storage, and route handling stays at the existing runtime boundary.

## Verdict (one-command probe)

`PYTHONDONTWRITEBYTECODE=1 $RT.venv/bin/python prototypes/gemini-runtime/probe_session_seam.py` printed full `LiveSession` state after each action: prepared S00 base commit 1/1 accepted; first diarized rolling update 1/1 accepted; later correction to the same rolling interval 0/1 accepted (`not_at_frontier`). Thus unmodified `LiveSession` cannot show later Gemini identity repair. Choose the narrow new operation that replaces labels and segment boundaries over an already-owned rolling interval while preserving its exact concatenated text. Keep `LiveSession` as state and snapshot authority; no separate session document. The operation must reject changed words and intervals it does not own. A separate narrow speaker registration call is needed because the old identity preparer is tied to a MOSS decode.

The probe is throwaway; remove its script after the verdict is in the design doc.

## Counter contract (lead requirement)

- **Structural question:** Can a harness distinguish provider calls, retries, failures, timing repair, audio sent, and cost for each meeting without reading transcript or audio content?
- **Minimum primitives:** session ID as owner; cumulative counters by call kind and error/retry code; clamped/dropped timing counts; sent audio seconds; USD cost. These are the facts that alter quality, spend, or failure interpretation; no transcript, speaker label, audio, API key, or provider request body belongs here.
- **Invariants:** additive nonnegative deltas; sessions isolated; readout is a copy; every provider call records the audio duration and cost once; error/retry code names are stable metadata. A cached call records no audio sent and no cost.
- **Assumptions / unknowns:** actual Gemini usage metadata and anomaly denominators arrive from the phase-2 adapter. The fake can prove accounting and isolation, not provider truth.
- **Falsifier:** two fake sessions with different usage/error events cannot produce separate content-free totals and per-kind/per-code counts.
- **Tool decision:** a one-command in-memory aggregation probe prints both meeting states and rejects negative deltas; then an offline runtime test verifies the same behavior through the public diagnostics method. This changes the engine factory interface by one reporting callback.
- **Verdict:** the probe printed isolated states for 2/2 sessions: rolling calls 2 vs terminal calls 1; only the first session had a 429 error/retry and 1 clamped / 2 dropped words; audio and cost remained 10 s / $0.03 vs 20 s / $0.02. The production-path fake test passed with copied readouts and a content-bearing code rejected. The throwaway script was removed.

## Phase 2 structural contract (before research or implementation)

- **Structural question:** Can a complete 60-minute mixed recording and its live sample clock feed real Gemini without dropping audio or publishing duplicate/unstable speaker rows, while Account and browser ownership stay unchanged?
- **Minimum primitives:** complete accepted-audio source; bounded Gemini request returning timestamped local-speaker words; scheduler choosing owned windows/frontier; meeting speaker registry; `LiveSession` publication; WeSpeaker observation keyed by meeting ID. The source prevents tail loss; requests provide speech evidence; scheduling gives a single owner per interval; registry stabilizes local labels; session handles display/lifecycle; voice observations bridge to cross-meeting names.
- **Invariants:** accepted samples equal retained full-recording samples before finalization; requests contain only public audio; provider key never enters telemetry; every attempt has content-free usage; terminal chunks cover the full recording with ≤30-minute requests; registry IDs never renumber; rolling ownership advances monotonically; preview begins at the committed prefix; 45-second degradation preserves words and retention; voiceprint encoder ID/dimension match stored samples; errors settle visibly and release scratch.
- **Assumptions / unknowns:** quality, latency, speaker continuity, costs, and anomalous word-offset rates are unmeasured for this pane until a 1.0× public-audio run. The placeholder window/word/registry policies are decisions from the lead, not winners. Account audio staging availability before terminal settlement and its access seam are unknown until code inspection.
- **Falsifiers:** a 60-minute synthetic mixed tape cannot round-trip before `finish`; the 45-second rule cannot keep accepted-minus-committed below retention while preserving a preview tail; a final chunk boundary duplicates/drops words or cannot map labels to live IDs; two same-voice public meetings cannot exercise voiceprint enrollment/auto-name through the existing Account path; a paced public HTTP run cannot settle with accounted audio and visible finalization.
- **Tool decisions:** inspect the tape/Account stage seam before choosing storage; a throwaway 60-minute round-trip probe decides whether existing retention suffices. Prototype the 45-second publication state and chunk overlap with printed full state before product code. Offline TDD checks exact wire and provider retry parsing using fake transports; one capped real public call checks SDK behavior; a 1.0× HTTP run checks latency/counters. Existing quality harness remains the scorer.

## Phase-2 tape probe verdict

`PYTHONDONTWRITEBYTECODE=1 $RT.venv/bin/python prototypes/gemini-runtime/probe_phase2.py` wrote 360 contiguous ten-second chunks (57,600,000 samples; 115,200,000 bytes) through production `CompleteMixedTape`; accounting reported complete and first/last 16,000 samples round-tripped exactly. At 9,600,000 bytes the same tape degrades after 300 seconds; `LiveMeetingAudioStages` independently uses the descriptor's same bound. A Gemini descriptor needs at least 115,200,000 bytes for 60 minutes, and Account will then retain its canonical stage. The scratch tape remains necessary under the current `finish(tape)` seam; later reuse of Account stage would require changing the ownership/read seam. The exploratory LiveSession frame constructor error was corrected; 10 accepted seconds produced 160,000 retained and 0 committed samples.

## Phase-2 real-call failure and normalization probe

The first paced `interview_bill_ackman_60s` HTTP attempt reached 24/60 seconds, then Account interrupted because `GeminiRolling` returned `segments_out_of_order`. Structural question: how can unordered/overlapping provider word offsets enter the single ordered, nonoverlapping `LiveSession` surface while preserving every word? Minimum primitives: absolute word bounds, deterministic chronological order, monotone display cursor, owned interval. Invariant: each published word remains present once; bounds stay within its owned interval and no row overlaps its predecessor. Unknown: count of words requiring a one-sample displacement on real corpus. Falsifier: a normalized window still gets `segments_out_of_order`, or an annotation word disappears. Tool: one-command synthetic probe against `LiveSession`, then repeat the same public case; a failure changes the normalization algorithm.

Verdict: the one-command probe printed 3/3 words retained and 2/2 boundaries nonoverlapping after chronological order and cursor displacement. The production `ordered_segments` policy now clips to each owned interval; if the interval is exhausted, it appends remaining text to its last row. This is a visible speaker-attribution limitation in fully overlapping speech; the same public HTTP case is the falsifier.

## C3 embedding handoff probe contract

Structural question: can one WeSpeaker vector computed from a Gemini-attributed window serve both the live continuity registry and Account's cross-meeting Voiceprint observation? Minimum primitives: one local speaker interval of ≥2 seconds, pinned encoder vector, local-to-meeting ID assignment, immutable observation. Invariants: no vector crosses meeting ownership or enters public diagnostics; the registry sees the vector before assignment, while Account sees the same vector under the assigned meeting ID. Unknown: added live latency from window embedding on public audio. Falsifier: an injected registry cannot observe the exact vector later exposed as an Account observation. Tool: a fake encoder/registry one-command test prints both vectors and identity; equality determines whether to remove duplicate runtime embedding on real engine updates.

Verdict: the one-command production-engine handoff probe printed registry `spk:0` vector `(0.6,0.8)` and Account `speaker-0001` observation vector `(0.6,0.8)`, exactly equal, 1/1. The registry receives embeddings before identity assignment; the update carries the same vector under the assigned meeting ID. The script was removed after the verdict; the equivalent fake-path test stays in `tests/gemini/test_gemini_hybrid_engine.py`.

## Canonical Account stage reuse probe contract

Structural question: does the existing Account mixed stage provide a complete, readable terminal source before settlement, while a bounded recent-audio cache suffices for live 60-second windows? Minimum primitives: Account-owned append-only PCM path, accepted sample count, read-only range view, 60-second rolling cache. The stage is durable source custody; the view avoids a second 115.2 MB copy; the cache serves live requests while transport is still appending. Invariants: terminal view sample count exactly equals accepted samples at Stop; view release never deletes Account's stage; cache memory stays ≤1,920,000 bytes; every live requested window within the most recent 60 seconds reads exactly. Unknown: cross-route ordering of final stage append until stop drain; source inspection shows mixer tees accepted output before runtime Stop. Falsifier: a synthetic 60-minute stage read misses head/tail, or a 60-minute live cache exceeds 60 seconds / returns wrong recent samples. Tool: one-command bounded-cache and stage-file probe, then a real paced HTTP rerun if the design changes.

Verdict: the one-command production `LiveMeetingAudioStages`/`_AccountStageTape` probe wrote 360/360 ten-second chunks (57.6M samples, 115.2MB), reported complete, read first and last 16,000 samples exactly, and left the Account stage file present after releasing the Gemini view. The bounded cache prototype held exactly 1,920,000 bytes after 60 minutes and returned the latest samples exactly. The exploratory scripts were removed. In the Account HTTP path, bind the reserved stage before session create and use that source for terminal reads; direct runtime tests retain `CompleteMixedTape` for isolation.

### Live cache stride-boundary correction

**Question:** Can a 60-second scheduled window still be read when accepted audio is between 10-second schedule boundaries? **Hypothesis:** the live cache needs window length plus one stride, 70 seconds. **Falsifier:** a scheduler-produced window begins before the retained cache at any accepted sample position. **Tool:** one-command production `FixedWindowScheduler` arithmetic probe at 60, 60.5, 69.5, and 70 seconds; an uncovered window changes the cache bound. **Full state:** at 60.5 seconds the requested window was 0–60 seconds but the old 60-second cache began at 0.5 seconds; at 69.5 seconds it began at 9.5 seconds. The 70-second cache covered all four positions. **Verdict:** set cache to 70 seconds (2.24 MB) while keeping the scheduler's 60-second window. A focused production-engine test blocks a rolling call, advances capture to 69.5 seconds, resumes the worker, and passes. The earlier 60-second cache probe was valid for size but insufficient for schedule coverage; this correction supersedes that cache-size conclusion. The Account 60-minute stage conclusion is unchanged.
