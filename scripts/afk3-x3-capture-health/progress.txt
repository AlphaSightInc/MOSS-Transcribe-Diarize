DEFECT FOUND AND FIXED DURING REVIEW

The terminal reason was a one-shot. live_transport._snapshot_response derived the terminal
capture facts from the since_version-gated snapshot, so the polling client's *next* tick —
carrying the version it had just been handed — got unchanged=true, no snapshot, and no helper
presence (teardown had released it), and the projection answered capture_phase "starting" /
"Waiting for audio capture to start." for a session that had already died. live_portal.py
polls exactly that cursor on every tick, so in the shipped client the readable reason would
have survived one tick before being replaced by a confident wrong answer — worse than the 403
it replaced. Fixed by reading the session as it is and applying the caller's cursor only to
the transported snapshot. Regression test:
tests/test_live_api.py::LiveApiTest::test_terminal_capture_reason_survives_the_polling_clients_since_version_tick
(fails 'starting' != 'failed' with the fix reverted). Scenario 7 of review-01 covers the same
thing at the artifact level, on both transports.

  getDisplayMedia rejection, a worklet, or a hidden tab. Every "browser_*" failure code is

REPORTED, NOT FIXED — needs an owner decision

a. Clean stop reports capture_phase "failed". _terminal_capture_status maps a session status of
   "closed" to phase "failed" with the line "Audio capture stopped.". The reference UI's
   CapturePhase union is starting|capture_alive|awaiting_audio|recording|failed and
   describeLiveSessionStatus renders capture_phase === "failed" as "Live session failed" with an
   error tone, before it looks at anything else. A user who stops their own meeting would be
   told it failed. The line is right; the phase is not, and there is no terminal-success value
   in the reference vocabulary to use instead. Not fixed here because inventing a sixth phase
   value changes a contract this ticket does not own and collides with x6.

b. Access bindings are now retained forever. Removing access.release_session from the terminal
   cleanup (live_helper_failure access=None) and from the stop/abort routes is what makes the
   reason readable, but LiveAccessRegistry._sessions is now only ever emptied by device
   revocation: measured 10 retained entries after 10 clean stops. Cost is small but unbounded —
   10,000 retained bindings is ~2.4 MiB and adds ~0.45 ms to the linear view-token scan that
   runs on every view-authorized request. live_auth.py is not owned by this ticket, so no
   retention bound was added. Post-terminal, the owning capture credential can also still POST
   /heartbeat (200, re-registering helper presence on a dead session) and re-POST /abort (200);
   both were 403 before.

c. Post-terminal mono frames now return 429, not 403. The v1 frame route re-raises the runtime's
   terminal failure, which _failure_status maps to 429 for kind transport_pacing regardless of
   the failure's own retryable=false. 429 tells a client to back off and retry a session that
   can never accept another frame. The v2 lane route correctly returns 409. Pre-existing
   mapping, newly reachable; three existing tests were edited from 403 to 429/409 to accept it.

Prototype question: can one terminal-precedence table avoid contradictory session/capture
states while distinguishing a clean user stop from failure? A throwaway driver exercised the
real `project_live_capture_status` seam for active, closed, aborted, failed, and closed-with-lane-

The owner also selected permanent conflict semantics for frames sent after terminal failure.
`_failure_status` now returns 429 only when a pacing failure is explicitly retryable; a retained
non-retryable terminal pacing failure returns typed 409, matching the v2 lane route and preventing
retry-forever behavior.
