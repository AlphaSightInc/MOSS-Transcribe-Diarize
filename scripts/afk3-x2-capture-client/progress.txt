--------------------------------------------------------------------------------
Defects found in the branch and fixed here
--------------------------------------------------------------------------------

A. Dropped-heartbeat race (introduced by this branch, P1). `scheduleHeartbeat` cleared
   its in-flight marker from a `.finally()` on the returned promise, leaving a
   one-microtask window where the drain loop had stopped but the marker still said it was
   running. A schedule landing there was never sent. Measured by scanning microtask
   offsets: offset 1 loses it. Worst case is `stop()`, which awaits this and would walk
   past its final `stopped` heartbeat — the one server behaviour PRD defect 2 exists to
   enable. Fixed with a boolean cleared inside `flushHeartbeat`'s own `finally`, in the
   same synchronous step the loop exits in. Two regression tests; reverting the fix fails
   four tests.

B. `browser_sustained_clipping` / `browser_microphone_silent` unbuilt (see 3 above).
   Thresholds measured on real audio: CLIPPED_FRAME_FRACTION 0.01,
   SUSTAINED_CLIPPING_FRAMES 4 (2 s), SILENT_MICROPHONE_FRAMES 20 (10 s, microphone
   only). Both ride `state: "degraded"`, never `"failed"`, because
   `LiveHelperFailureCoordinator.observe` calls `LiveV2Session.fail_lane` on a `failed`
   lane and two failed lanes tear the session down: a loudness warning must not end a
   meeting. Both clear on recovery.

--------------------------------------------------------------------------------
What the tests do NOT cover
--------------------------------------------------------------------------------

* No real browser, anywhere. Every "real event" test dispatches a real DOM event at a
  fake track / fake AudioContext. Chrome's actual `ended` / `statechange` timing, the
  attended display-capture picker, tab-vs-monitor surfaces, device replug, and the
  sticky-activation rules are all unexercised. The picker cannot be automated (a
  2026-08-03 CDP attempt failed with `NotReadableError`), so this gap closes only with an
  attended run.
* No live server. The frame path is exercised against an in-test fake. The fake's outcome
  table is pinned to the production `LiveLaneIngress` by a probe, but it does not
  exercise FastAPI routing, the auth registry, the mixer, the tape, or the real 429s from
  `InferenceArbiterBackpressure` / `LiveSessionBackpressure`. Nothing here proves an
  end-to-end capture session works.
* Clipping and silence thresholds are measured on 3 minutes of recorded 16 kHz audio and
  synthetic controls, not on a live Chrome capture. In particular no recording of the
  measured loopback-lane clipping exists in the tree; a gained speech corpus stands in
  for it. Whether 2 s / 10 s feel right to a user is unmeasured.
* `replaceLane` is exported and tested but no browser event in this client calls it. A
  track that ends latches the lane `failed` (which the server then seals), so the mic
  replug the PRD describes leads to session recreation, not lane replacement. The epoch
  path is therefore only reachable if the orchestrator wires a user-driven "switch
  device" action. A device swapped underneath a still-live track (Chrome changing the
  default input without firing `ended`) is neither detected nor tested.
* The three pre-session codes never reach the server, by construction: they occur before
  a session id exists, so there is no authenticated heartbeat to carry them. They reach
  the caller through `onPreSessionFailure`. The status-line copy for them lives on the
  server, so the orchestrator has to render its own text for those three.
* Backpressure is unbounded on the client. Under sustained lane-capacity 429 the per-lane
  `frameQueue` grows without limit; nothing caps it or drops from it. Untested and
  unmeasured.
* `stop()` discards whatever is still queued: those frames are neither sent nor counted
  into `dropped_frames`, so the final `stopped` heartbeat under-reports by up to the
  queue depth.
* HTTP 404 / 401 / 403 on the frame route are not classified. They fall through to the
  generic `throw` -> "unconfirmed" path, which counts a dropped frame, advances the
  sequence, and keeps posting to a session that may be gone. Only 400 / 409 / 429 are
  handled by name.
* Heartbeat delivery failures are reported to `onTransportError` and otherwise dropped;
  there is no retry and no test for a heartbeat that 409s on
  `HelperPresenceConflict`.
* `evidence/phase1/x2-capture-client/iteration-{6,7,8,9}-*.txt` are test-run transcripts,
  not measurements. They were re-run and reproduce, but they prove only that a test suite
  passed.
